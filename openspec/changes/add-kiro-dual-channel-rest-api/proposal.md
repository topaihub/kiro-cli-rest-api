# 需求说明：将 Kiro CLI 封装为 Zig REST API，并保持双通道架构语义

## 背景

AWS 官方文章《将 Kiro CLI 封装为 REST API：双通道架构实践》给出了一个可运行的 Python 参考实现：

- `acp_client.py`：ACP JSON-RPC 2.0 客户端
- `server.py`：FastAPI 服务

该实现的核心不是“做一个通用聊天接口”，而是忠实解决 Kiro CLI 的两个现实限制：

1. `kiro-cli acp` 支持多轮会话和流式更新，但不支持运行时切换模型。
2. `kiro-cli chat --model X ...` 支持指定模型，但本质是一次性子进程，不支持多轮上下文。

因此原文采用“双通道架构”：

- `model=auto`：走 ACP 通道，支持多轮会话
- `model!=auto`：走 Chat 通道，支持指定模型

本变更的目标不是重新设计一套全新接口，而是用 Zig 重建这一工程方案，并在保持原文意图的前提下做工程化优化。

## 目标

1. 用 Zig 实现与原 Python 版本等价的 REST API 服务。
2. 保持“双通道架构”的职责边界：
   - ACP 通道负责 `auto` 模型、多轮会话、流式收集、权限自动审批。
   - Chat 通道负责指定模型的单次调用与输出清洗。
3. 对外提供与原文一致的接口集合：
   - `GET /`
   - `POST /prompt`
   - `POST /sessions`
   - `POST /sessions/{id}/prompt`
   - `GET /sessions`
   - `DELETE /sessions/{id}`
   - `GET /models`
4. 保留原文中的关键协议发现：
   - `session/update` 是文本真正载体。
   - `session/request_permission` 必须同步回复。
   - ACP 最终响应只包含 `stopReason`，不包含正文文本。
   - Chat 通道输出必须做专门清洗。
5. 将工程组织为适合大模型继续开发的模块化 Zig 项目，并接入：
   - `zig-logging`
   - `zig-release`

## 事实基线

本变更以下列材料为事实基线：

1. AWS 官方原文对双通道架构的说明。
2. `kiro-acp` 参考实现中的：
   - `acp_client.py`
   - `server.py`

若 Zig 设计与上述基线冲突，应优先修正 Zig 设计，而不是反过来解释原文。

## 非目标

1. 不在本阶段引入公网鉴权、多租户或数据库持久化。
2. 不尝试绕过 Kiro CLI 的 ACP 模型切换限制。
3. 不在本阶段支持 Chat 通道多轮上下文持久化。
4. 不要求首版实现 ACP 并发复用或连接池。

## 基线行为

本变更以以下行为作为基线，后续 Zig 实现必须保持一致：

1. `model=auto` 时优先使用 ACP。
2. 只有在需要显式指定模型时，才降级到 Chat 子进程。
3. ACP 会话是内存态的、服务重启即丢失。
4. Chat 通道是无状态单次执行，不复用历史。
5. REST 层负责统一接口，不向调用方暴露 ACP/Chat 细节。

## 需要保留的已知限制

1. API 默认仅面向内网环境，无鉴权。
2. ACP 通道默认按单连接顺序处理请求。
3. 会话不持久化。
4. Chat 通道冷启动较慢。
5. ACP 路径的真正复杂点在于异步协议封装，而不是 HTTP 路由本身。

## 期望的工程化优化

在不破坏原文语义的前提下，可以做以下优化：

1. 用 Zig 模块边界替代 Python 文件内的混合职责。
2. 用显式内存管理和生命周期控制替代隐式对象行为。
3. 增加结构化日志，记录：
   - 请求入口
   - 通道选择
   - ACP 事件
   - Chat 子进程失败
4. 增加更严格的错误映射和测试覆盖。

## 需要显式避免的偏差

1. 不能先发明一套 Zig 风格接口，再倒推说“符合原文精神”。
2. 不能在没有源码证据的情况下固定 `kiro-cli chat` 的参数细节。
3. 不能把“实现方便”凌驾于“双通道职责边界”之上。

## 交付物

1. OpenSpec 设计与任务拆分工件。
2. Zig 项目中的模块化实现方案说明。
3. 后续可由大模型直接执行的任务列表。
